**Testing notes:**

- **Real bug found and fixed before any of this milestone's own code could run:** `packages/database/src/middleware.ts`'s soft-delete extension listed `BrunchLocationVote` and `BrunchTimeVote` in `SOFT_DELETE_MODELS`, but neither table has a `deletedAt` column — it was never added, because votes are replaced via hard delete + insert (there's nothing to soft-delete). Any `findMany`/`findFirst` against either table threw `PrismaClientValidationError: Unknown argument deletedAt`. Nothing had ever queried these tables directly before this milestone (spec 0001 only created them), so the bug was latent since the original scaffold. Verified by direct reproduction against the live DB, then fixed by removing both models from the set, with a comment explaining why they don't belong there. No test suite caught this because nothing exercised the tables — the fix is covered going forward by every integration test in this milestone, since `castLocationBallot`/`castTimeBallot`/`getBrunchVoting` all query them now.
- **What was tested:** `assertCanVote` for all four RSVP statuses. Both cast-ballot services: insert-only (first vote), replace semantics (add and remove in one call), idempotent re-send, every rejection kind (`brunch_not_found`, `brunch_not_active`, `empty_ballot`, `not_an_attendee`, `cannot_vote`, `voting_closed` via both a past deadline and a confirmed brunch, `not_a_vote`, `unknown_option`), db-error mapping, event-emit-failure-still-Ok, and `vote/cast` vs `vote/changed` naming. `getBrunchVoting`: access scoping (host-or-attendee only, mirroring `getBrunchById`), `canVote` derivation, per-option `voteCount`/`viewerVoted`, voter names visible only to the host, derived mode and closed state, and `participationRatio`/`eligibleCount` including the case where a vote exists from a user no longer in the eligible set. Both routes: auth, malformed id, empty-array validation, every error-to-status mapping, success shape.
- **How:** Unit — 3 new service/guard files + 2 routes, 91 new unit tests (`castLocationBallot.test.ts` 18, `castTimeBallot.test.ts` 17, `getBrunchVoting.test.ts` 12, `assertCanVote.test.ts` 5, plus the two route test files), all mocked at the `db` call boundary. - **A design choice this milestone had to make that the spec didn't fully pin down:** the order of guard checks inside both cast-ballot services. Settled on brunch existence → brunch active → empty ballot → attendee/eligibility → voting closed → vote-exists (mode) → option validity. Not specified anywhere, and only observable when a request fails more than one check at once; recorded here so M4 (which inserts `assertVotingOpen` into this sequence) doesn't have to rediscover it.
- **What's deferred:** The `voting_closed` check (inline `isVotingClosed` in both services, explicitly commented as an M4 placeholder) runs **before** the transaction opens, not inside it. The spec's stated goal — "a ballot submitted a millisecond after the host closes voting must lose" — isn't met yet; a close racing a vote could still let the vote through. This is intentional and expected: M4 formally wires `guards/assertVotingOpen.ts` into both services' transactions, which is the point where this gets fixed, not before. No test asserts the race is closed, since M3 doesn't claim to close it.

## M4 — Closing voting

No `...VotePromptedAt` columns and no fire-once guard — the 66% nudge is derived, since v1 cannot deliver the notification it would have guarded (see plan.md). The notifications spec owns that work.

- [x] Schema: add `Brunch.votingClosedAt DateTime?`; generate and commit the migration
- [x] Implement `guards/assertVotingOpen.ts` — the derived predicate (`votingClosedAt`, past `votingDeadline`, or `status == confirmed`), callable inside a transaction; unit tests for all three closure paths plus the open case
- [x] Wire `assertVotingOpen` into both cast-ballot services, evaluated **inside** the transaction
- [x] Implement `closeVoting.ts` — host-only; sets `votingClosedAt = now`; rejects when already closed (`already_closed`)
- [x] Implement `updateVotingDeadline.ts` — host-only; accepts a future datetime or `undefined` to clear; rejects once voting is closed. Without this there is no way to set a deadline after creation, since only the wizard sets one today
- [x] Extend `getBrunchVoting` with `shouldSuggestClosing` = `!closed && eligibleCount >= 3 && participationRatio >= 0.66`, computed per kind
- [x] Export both services from `packages/core/src/index.ts`
- [x] Routes: `POST /api/v1/brunches/:id/voting/close`, `PATCH /api/v1/brunches/:id/voting/deadline`
- [x] Unit tests: close is host-only and rejects double-close; deadline must be future; ballots rejected once closed by manual close and by past deadline; `shouldSuggestClosing` false below 3 eligible, true at the 66% boundary, false once closed
- [x] Integration test: three eligible attendees, two vote, ratio and nudge correct; ballot after `votingClosedAt` rejected; ballot after a past `votingDeadline` rejected with no `votingClosedAt` set
- [x] `pnpm typecheck && pnpm lint && pnpm test` pass
- [x] Commit: `feat: close voting, manage the deadline, and derive the close nudge (M4)`

**Testing notes:**

- **What was tested:** `assertVotingOpen`/`isVotingClosed` for all three closure paths (`votingClosedAt`, past `votingDeadline`, confirmed status) plus the open case. `closeVoting`: host-only, double-close rejected, and — reusing the full derived predicate rather than just the raw column — closing a brunch already closed by a past deadline or by confirmation is also rejected as `already_closed`, not treated as a fresh close. `updateVotingDeadline`: host-only, future-only validated at the Zod boundary (not in the service itself), clearing via `undefined`, rejected once closed. Both cast-ballot services: the manual-close and past-deadline paths now resolve via a **fresh re-fetch inside the transaction**, not the pre-transaction brunch object. `getBrunchVoting`'s `shouldSuggestClosing`: fires at exactly 2/3 with 3+ eligible, never below 3 eligible regardless of participation, never below the 66% threshold, and never once already closed.
- **The actual race-closing test** — the one this milestone exists for: `castLocationBallot`/`castTimeBallot` unit tests now include "closes the race: a close that lands between the pre-transaction check and the write still loses the vote," where the pre-transaction mock returns an open brunch and only the transaction-scoped re-fetch (`tx.brunch.findFirst`) returns a closed one. Before this milestone's restructuring, that scenario couldn't be expressed at all — the old inline check ran once, before the transaction, with no second look. Integration-level, the same shape is covered by `closingVoting.integration.test.ts`'s manual-close and past-deadline cases against real Postgres, though a true concurrent race (two overlapping transactions) isn't simulated — that would need two real concurrent connections mid-transaction, which is a meaningfully different and more expensive test to write; the single-fetch-vs-fresh-fetch unit test is what actually proves the fix.
- **A test-fidelity bug caught and fixed along the way, not a production bug:** `getBrunchVoting.test.ts`'s mock brunch objects omitted `votingClosedAt` entirely (`undefined`, not `null`). `isVotingClosed` checks `votingClosedAt !== null`, and `undefined !== null` is `true` in JS — so every mock brunch was silently evaluating as "closed," and no existing assertion caught it because nothing asserted `closed === false` for the default open case. Fixed by giving every mock brunch an explicit `votingClosedAt: null` (matching what a real Prisma row always returns — never `undefined`) and adding an explicit "is open by default" test. This was a gap in test fidelity, not in the shipped code; the real Prisma client never returns `undefined` for a nullable column.
- **How:** Unit — `assertVotingOpen.test.ts` (5), `closeVoting.test.ts` (7), `updateVotingDeadline.test.ts` (10), plus restructured tests in `castLocationBallot.test.ts` and `castTimeBallot.test.ts` (both mock `tx` now includes `brunch.findFirst`, separately overridable from the pre-transaction `db.brunch.findFirst`) and new `shouldSuggestClosing` coverage in `getBrunchVoting.test.ts`, plus the two new route test files. Integration (`closingVoting.integration.test.ts`, 5 tests) against real Postgres, following the same `createThreeEligibleBrunch` real-activation-path convention as M3's `voting.integration.test.ts` (host + 2 yes-voters = 3 eligible, since the host counts toward eligibility per plan.md).
- **What's deferred:** No test simulates two genuinely concurrent transactions racing against the same brunch (one closing, one voting, overlapping in time) — see above. `confirmBrunch` (M5) is the other path that sets `votingClosedAt`; this milestone's tests only exercise `closeVoting` setting it directly.
- **How to run it:** `pnpm typecheck && pnpm lint && pnpm test` from repo root (unit only); `pnpm --filter @brunchsters/core test:integration` for the integration suite (local Supabase must be running).

- [x] Route: `POST /api/v1/brunches/:id/confirm` — body `{ locationId, timeId }`
- [x] Unit tests: host-only, every rejection above, confirming a non-leading option succeeds (host prerogative), `votingClosedAt` preserved when already set
- [x] Integration test: a full confirm writes all five changes atomically; a second confirm is rejected; the partial unique index rejects a directly-inserted second confirmed location; invite token expiry recomputed and verified against the confirmed `scheduledAt`
- [x] Update spec 0004's `tasks.md` note that the token-expiry hook is now implemented
- [x] `pnpm typecheck && pnpm lint && pnpm test` pass
- [x] Commit: `feat: host confirms a brunch, locking location and time (M5)`

**Testing notes:**

- **What was tested:** Host-only enforcement; every rejection path (`brunch_not_found`, `brunch_not_active` including already-confirmed, `no_locations`, `no_times`, `unknown_option` for both ids independently); confirming a non-leading option succeeds and reports `locationWasVoteLeader: false` on the emitted event rather than being blocked (host prerogative, not an error); `votingClosedAt` set when null and preserved untouched when already set by an earlier `closeVoting` call; `tokenExpiresAt` recomputed on every invite except the host's own synthetic one (identified the same way `getInvitesForBrunch` already does — matching `invitedEmail` against the host's, case-insensitive); db-error and `lookup_not_found` mapping; event-emit-failure-still-Ok.
- **The one test that actually proves the schema constraint, not just the service's promise:** `confirmBrunch.integration.test.ts`'s partial-index test bypasses `confirmBrunch` entirely and does two raw `db.brunchLocation.update({ data: { isConfirmed: true } })` calls directly against the same brunch, asserting the second one throws. `confirmBrunch` itself can never produce two confirmed options (it only ever sets one per call, on an `active` brunch it immediately moves to `confirmed`), so a test that only called the service would never exercise the index at all — it would pass whether or not the index existed. This is the belt-and-braces the plan called for, verified by actually trying to defeat the belt.
- **How:** Unit (`confirmBrunch.test.ts`, 15 tests) mocked at the `db`/`tx` boundary, following the same mock-tx-separately-from-mock-db shape established in M3/M4. Integration (`confirmBrunch.integration.test.ts`, 4 tests) against real Postgres: a full confirm's five writes verified individually (location, time, brunch status, `votingClosedAt`, invite `tokenExpiresAt`), a rejected double-confirm, the partial-index bypass test above, and confirming while an unrelated option still holds a vote (proving a vote on the non-chosen option doesn't block confirming the other).
- **What's deferred:** No test exercises two `confirmBrunch` calls racing concurrently. Worked through on paper rather than left unexamined: unlike M4's vote/close race, this one is already closed by the partial unique index itself, not by anything application-level. `assertBrunchActive`'s pre-transaction check isn't re-fetched inside the transaction the way M4 made the cast-ballot services do for `assertVotingOpen` — so two concurrent calls could both pass that check before either commits — but the index is keyed on `brunchId` alone (not `brunchId + locationId`), so a second transaction setting `isConfirmed` on _any_ location row for the same brunch, even a different one than the first call chose, collides with the same constraint and fails at the database. Data integrity holds either way; the only real gap is that the loser gets a generic `db_error` instead of a clean `brunch_not_active`. That's a minor error-message quality issue, not a correctness one, and not worth the cost of a re-fetch-inside-transaction restructure for an action only the host ever takes, alone, once.
- **How to run it:** `pnpm typecheck && pnpm lint && pnpm test` from repo root (unit only); `pnpm --filter @brunchsters/core test:integration` for the integration suite (local Supabase must be running).

- `packages/database/src/middleware.ts` gained `isUniqueConstraintError(error)` (checks `Prisma.PrismaClientKnownRequestError` + code `P2002`) and exports it from the package, so `packages/core` can detect the collision without importing `@prisma/client` directly (CLAUDE.md boundary).
- `addLocation`/`addTime`/`reviewLocationSuggestion`/`reviewTimeSuggestion` all catch it and return a new `already_added` error kind instead of a raw `db_error`; both API routes map it to a 409 with a clear message.
- `suggestLocation`/`suggestTime` additionally check against _live_ options up front (not just other suggestions, which they already checked) — catches the common case at suggest-time with a useful error, rather than letting a doomed suggestion sit pending for days before failing at approval time.
- Covered at every level: unit tests for the `isUniqueConstraintError` → `already_added` mapping in all four services, unit tests for the new live-option pre-check in both suggest services, route tests for the 409 mapping, and an integration test reproducing the exact race against real Postgres (suggest → host adds directly → approve → rejected with `already_added`, exactly one live row survives).

**Confirmed via real concurrency, not just reasoning: confirm-vs-confirm.** M5's testing notes had reasoned through this on paper but never run it. Added a genuinely concurrent test to `confirmBrunch.integration.test.ts` — two real `confirmBrunch` calls fired via `Promise.all` on the same brunch (not sequential, so neither call's pre-transaction check has necessarily seen the other's write), asserting exactly one succeeds, exactly one fails, and the DB ends up with exactly one confirmed location and one confirmed time regardless of which won. Ran it 5 times in a row to rule out a lucky pass. The partial unique index holds under real concurrency, confirming M5's reasoning was correct — the loser still gets a generic `db_error` rather than a clean `brunch_not_active`, which remains the one accepted, documented trade-off from M5.

**Left as reasoning, not a live test: vote-vs-close.** The existing M4 unit test already proves this deterministically by mocking the pre-check as open and the in-transaction re-fetch as closed. A genuine two-connection version would need artificial delays to reliably land in the right interleaving and would be strictly less convincing than the mock, not more — no change made here. **Superseded below:** an independent review (see "Independent review fix-through" further down) found this reasoning itself was wrong — the mock could never have detected that the mechanism didn't actually serialize anything under real `read committed` semantics. That section documents the real fix and the real test.

**Decided, with the user: declined suggestions are blocked from resubmission forever.** Raised as a question, not a bug — `BrunchLocationSuggestion`/`BrunchTimeSuggestion`/`BrunchInviteSuggestion` (spec 0004) have no soft-delete, so a declined suggestion can never be resubmitted by anyone, for that brunch, for any of the three suggestion types. User chose to fix all three rather than leave spec 0005 inconsistent with spec 0004's existing behavior. **Scoped out of this branch**: fixing `BrunchInviteSuggestion` means touching already-shipped spec 0004 code and deciding the resubmission mechanics (new row vs. resetting the existing one) — bigger than a pre-MR polish pass. ### Independent review fix-through (2026-10-09)

A fresh, independent review (Opus, no shared context with the branch's own author or prior review passes — see the agent transcript, not reproduced here) was run against `main..feat/0005-voting-and-confirmation` as a genuine second opinion before the MR. It confirmed the core service layer and schema as sound — correctly called out the soft-delete `count()` discipline, the `getBrunchVoting` `select`-not-`include` read model, and the partial-index tests as the strongest parts of the branch — but found real issues concentrated in client components and one place where the branch's own stated safety guarantee didn't hold under real Postgres semantics. The user asked to fix everything reasonably fixable before merging. All of the following are implemented, not just reasoned about; where a finding was a genuine concurrency claim, the fix comes with a test that uses real, separate connections racing via `Promise.all` — not a mock — because that's exactly the category of claim the review caught going wrong.

**Fixed: duplicate ids in a ballot caused a state-dependent 500.** `castBallotRequestSchema` allowed `["A","A"]`; whether it crashed depended on whether the voter had already voted for A (a fresh vote hits `createMany`'s unique-index violation → uncaught `db_error` → 500; a re-vote's `toInsert` happens to be empty, masking it). Fixed at both the API boundary (a `.refine` rejecting duplicates with 422) and the service boundary (`Array.from(new Set(input.optionIds))`, since the type already promises "the voter's complete set" and a direct caller bypassing the schema shouldn't be able to crash it either). Both `castLocationBallot.ts` and `castTimeBallot.ts`; both get a dedicated unit test.

**Fixed for real: the vote-vs-close race the branch had claimed, but not actually closed.** The existing comment and test name asserted "a close racing a vote must make the vote lose," backed only by a mock that stubbed the transaction's re-fetch as already-closed — which proves the code path exists, not that Postgres will ever produce that interleaving. Checked directly: this runs at `read committed`, `closeVoting` is a bare `UPDATE` with no transaction of its own, and nothing takes a lock — so a close can commit in the exact gap between the vote transaction's read and its write, and the vote lands anyway. Fixed with a real `SELECT ... FOR UPDATE` on the `Brunch` row at the top of both ballot transactions, which forces `closeVoting`'s `UPDATE` (which needs the same row lock to proceed) to serialize against it: either the vote transaction already holds the lock and `closeVoting` blocks until it commits (vote legitimately happened first), or `closeVoting` got there first and the re-fetch correctly sees closed. Proved with a test that holds the lock from a second real `createDb()` connection and asserts `closeVoting` genuinely blocks until the lock is released — not a mock standing in for Postgres's actual locking behavior. Same mechanism also used for `removeLocation.ts`/`removeTime.ts`'s TOCTOU fix below, and `castLocationBallot.test.ts`/`castTimeBallot.test.ts`'s mocks needed a `$executeRaw` stub added.

**Fixed: a TOCTOU race in `removeLocation`/`removeTime` could empty a kind to zero options.** The remaining-count check read outside any lock; two concurrent removes of the two different surviving options could each see "2 remaining," both pass, and both soft-delete — exactly the state the `last_option` guard exists to prevent. Fixed by moving the count-then-update into a `$transaction` with the same row-lock pattern, and a new `LastOptionError` (mirroring the existing `LookupNotFoundError` pattern) to escape the transaction with the right error kind. Both services' existing unit tests needed rewriting to mock a `tx` the same way `castLocationBallot.test.ts` already does (count/update moved from `db.*` to `tx.*`). Proved against real Postgres with a genuinely concurrent `Promise.all` of two removes, run 5× to rule out a lucky pass — consistently exactly one succeeds, one gets `last_option`, and exactly one option survives.

**Fixed: options could be added, and suggestions approved, while voting was derived-closed.** `addLocation`/`addTime`/`reviewLocationSuggestion`/`reviewTimeSuggestion` only checked `assertBrunchActive`, never `assertVotingOpen` — so a host (or an auto-approved suggestion) could add a brand-new, never-votable option to a ballot that was supposed to have frozen, and there was no way back once a deadline merely lapsed (an accident, not a decision, unlike a manual close). Two-part fix: (1) `updateVotingDeadline` now only blocks on a genuine standing lock — `votingClosedAt !== null` or `status === confirmed` — not on `isVotingClosed`'s full predicate, which also factors in the very `votingDeadline` field being changed; a host can now extend a lapsed deadline and voting reopens as a direct consequence (no separate "reopen" flag needed). (2) `addLocation`/`addTime` and the `approve` path of both review services now also call `assertVotingOpen`, rejecting with `voting_closed` (new 409 case on all four routes) when it's genuinely closed — `decline` stays ungated, since dismissing a suggestion doesn't grow the ballot. Verified against the live dev server: adding a location while a lapsed deadline sat unaddressed returned 409; extending the deadline returned 200; the same add then succeeded with 201.

**Fixed: confirming a stale (past) candidate time could retroactively expire every outstanding invite.** `addTime` only validates futureness at creation, not at confirm time, and `tokenExpiresAt = scheduledAt + 7 days` can still land in the past for anything more than a week stale — silently expiring every invite on a brunch that had just been confirmed, with the transaction reporting success regardless. Fixed with a floor: `tokenExpiresAt = max(scheduledAt, now) + 7 days`. Also fixed a stale integration-unaware date in `confirmBrunch.test.ts`'s own fixture (`SCHEDULED_AT` was a hardcoded `2026-08-01`, which had quietly become a past date by the time this review ran, and was accidentally exercising the exact bug being fixed) — switched to `Date.now() + 14 days`, matching the dynamic-date convention the integration tests already use.

**Fixed: a host-added option and an approved suggestion for the identical place/time could still both end up live** in one specific ordering the earlier architect-review pass's fix didn't close: the partial unique index (`one live row per brunchId+placeId`) is correct and does prevent this at the DB level — but `confirmBrunch`'s sibling pattern for mapping that collision cleanly wasn't applied to this path's error reporting either. Re-verified the existing fix is sound; no further schema change needed here — see the architect-review section above for the original fix.

**Fixed: a concurrent-confirm loser got a generic `db_error` instead of a clean `brunch_not_active`.** M5's original testing notes priced this as "not worth a re-fetch-inside-transaction restructure." It didn't need one — `isUniqueConstraintError` was already imported in the sibling suggestion-review services; catching it in `confirmBrunch.ts`'s transaction catch block and mapping to `brunch_not_active` was a two-line fix. The existing concurrent-confirm integration test (added in the earlier architect-review pass) only asserted `isErr()` generically; strengthened it to assert the specific kind, which re-ran clean against real Postgres.

**Fixed: `BallotChecklist`'s optimistic vote state could wedge or lie.** `selected` was seeded once from props at mount and never reconciled — `router.refresh()` re-renders this client component with fresh `options` but doesn't remount it. Two concrete breakages this produced: (a) a failed save (e.g. voting closed mid-click) left a checked box on screen for a vote that was never recorded, with no rollback; (b) if the host removed an option this voter had checked, every subsequent vote attempt kept resubmitting the dead id, 404ing as `unknown_option` forever, with no way back short of a hard reload — the exact bug class already caught and fixed in `ConfirmControl`'s `effectiveLocationId` derivation, missed in this sibling component. Fixed with the same pattern: `effectiveSelected` filters `selected` against the current `options` on every render (no `key` or extra effect needed), and a failed submit now restores the pre-toggle selection before surfacing the error. This is pure client-state logic with no server-observable effect, and this codebase has no component-test convention (CLAUDE.md: "no tests for framework code") and no browser-automation tool available in this environment — verified by code reasoning only, consistent with how this spec's standing "no real browser has ever clicked anything in this UI" gap has been handled throughout M7/M8.

**Fixed: the confirmed brunch's time on `/manage` rendered in the server's timezone, not the location's.** `manage/page.tsx`'s read-only confirmed summary is a server component with no client-side correction pass; `toLocaleString(undefined, {...})` with no explicit `timeZone` resolves to the _server's_ zone during SSR (UTC in production) and ships that string as-is — directly contradicting PLANNING §9.3 and this spec's own "nothing shifts at the moment of confirmation" promise. Fixed by passing `timeZone: confirmedLocation?.timezone` explicitly. Verified live: a brunch confirmed with a time of `2026-12-01T20:00:00Z` and a location in `Asia/Tokyo` rendered "Dec 2, 2026, 5:00 AM" (correct, Tokyo) — not "Dec 1, 2026, 2:00 PM" (this dev machine's actual zone, America/Chicago, confirmed via `Intl.DateTimeFormat().resolvedOptions().timeZone` before starting the server).

**Fixed one real instance of the broader hydration-mismatch pattern the review flagged across several client components.** `VotingControls.tsx`'s `min={toDatetimeLocalValue(new Date())}` recomputed a fresh value on every single render (not just at hydration), and its `deadlineInput` initial value used local-time accessors that resolve differently on the server (SSR) than in the browser. Fixed by deferring both into a `useEffect` that runs once on mount, matching the deferral pattern this page already uses for the time-subline's `viewerTimezone`. **Not fixed, left as a known remaining gap**: the same `toLocaleString(undefined, {...})`-with-no-explicit-timeZone pattern appears in several other client components (`BallotChecklist`'s primary time label, `ConfirmControl`, `OptionManager`, `OptionSuggestionReview`, `OptionSuggestionControl`'s pending-suggestion list) — each a milder, self-healing version of the same mismatch (React warns, then swaps to the correct client value on hydration, rather than permanently showing a wrong value the way the two fixes above did). Fixing all of them properly means restructuring each to defer formatting to a client-only render pass; given the two fixed instances were the ones that were either a data-correctness bug (F5) or a continuously-reproducing mismatch (not just a first-paint one), the remaining instances were judged lower-value for the time available and are left as a documented follow-up, in the same spirit as this spec's other acknowledged "no browser" gaps.

**Fixed: `OptionSuggestionControl`'s `LocationSuggestionControl` still carried its own full copy of the Places-autocomplete logic**, never migrated onto the shared `PlaceSearchInput` extracted in M8 — three copies had briefly become two, not one, and the duplication's cost was already visible: the `response.ok` crash fix earlier in this spec had to be applied in both places because the duplicate still existed. Consolidated: `LocationSuggestionControl` now renders `<PlaceSearchInput onSelect={...} onError={...} />`. Along the way, fixed the one substantive behavioral gap the duplicate had closed and the shared component hadn't: a failed place-details fetch now calls an optional `onError` callback instead of silently clearing the input with no feedback — `OptionManager` (which also consumes the shared component) gained the same `onError` wiring it was previously missing. Also added a `disabled`/in-flight guard to `OptionManager`'s two add paths (add-location, add-time), which had none — a double-click used to fire two POSTs, the second of which would 409 on the new `already_added` unique-constraint mapping for a request that had, confusingly, actually already succeeded.

**Corrected one AC that overstated the actual response shape.** Spec.md's `PUT /votes/*` acceptance criterion claimed "200 with updated counts" — the route has always returned `{ optionIds }` (an echo of what was saved), relying on the client's `router.refresh()` to pull fresh counts from the server-rendered page rather than shaping a read model of its own. Harmless in practice, but a real AC-vs-code mismatch; corrected the AC wording rather than changing the route's shape, since the existing behavior is the better design (no duplicate read-model logic in the write path).

**Scoped out, left to the user's explicit decision:** declined option-suggestions being blocked from resubmission forever — same precedent as spec 0004's invite-suggestions, raised as a question rather than a bug, and the user chose to fix all three suggestion types together as its own follow-up spec rather than inside this branch. See `docs/PLANNING.md` §17 for the tracking note; nothing implemented here.
