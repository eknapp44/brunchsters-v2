- **A flaky test found by the mutation runs, and a real bug behind it:** `FileEmailService`'s "keeps send order" test failed in two of nine runs for mutations that had nothing to do with it. - **E2E journeys:** none added; M3 is wiring with no new screen or rule (the e2e server runs the no-op bus and the file outbox, so nothing about the suite's behavior changes). The e2e config does change, though: see the next item. N1–N4 are M4.
- **Findings the spec did not anticipate:**
  1. The developer's real `.env.local` carries `RESEND_API_KEY`, `INNGEST_EVENT_KEY` and `INNGEST_SIGNING_KEY`, and Next loads it into the e2e server too. With the new adapters selected by configuration, the e2e suite would have sent real events to Inngest Cloud and real mail. `playwright.config.ts` now blanks all of them (as it already did for `GOOGLE_PLACES_API_KEY`) and sets `EMAIL_OUTBOX_DIR` to a fixed temp directory (fixed because every Playwright worker re-reads this config, so a per-process path would differ; M4's global setup empties it).
  2. "Production" cannot mean `NODE_ENV=production`: CI and the e2e suite serve a production _build_ with `next start`. The check keys on `VERCEL_ENV=production` instead (ADR 0009, spec and plan corrected) and runs in `instrumentation.ts` at server start; the adapters are built lazily so `next build` needs no keys.
  3. The Inngest SDK's 401 for an unsigned request has the body `{"message":"Unauthorized"}`, while the app's own session gate answers `{"error":"Unauthorized"}`. N4 (M4) can therefore assert the body to prove the request got past middleware to the SDK, instead of just a status code.
  4. Inngest v4 differs from the v3-style API this plan was written against: triggers go in the function options (`createFunction({ id, triggers: [...] }, handler)`), and step output is stored as JSON, so the confirmed time travels as an ISO string and `undefined` fields (a recipient's missing name) disappear and are restored explicitly.
  5. A local `pnpm dev` with the developer's real keys now really sends mail (Resend sandbox: only to the account owner) and events to Inngest Cloud. `SETUP.md` tells the developer to blank those locally and use `INNGEST_DEV=1`.
- **Correction to this milestone's original task list:** the production check uses plain presence checks, not a Zod schema (a handful of "is it set" tests do not need one); the manual check used the e2e database and a throwaway script because the app has no UI path that sends mail without a signed-in browser session (M4's journeys do that properly); the `inngest` wrapper functions (`functions.ts`) have no unit tests of their own, only the pieces they call do, and they are exercised by the manual run above and by N1–N3.
- **What's deferred:** Nothing has called the real Resend API (fake client only), so Resend honoring the idempotency header and the sandbox `validation_error` mapping are as documented in its types, not observed. Inngest Cloud mode is unexercised (dev server only); in cloud mode the only thing checked is signature refusal. `instrumentation.ts` has not been run in a real production-mode boot (the function it calls is unit-tested); `middleware.ts`'s `/api/inngest` allowance has no unit test and is proven by N4 in M4. One `pnpm build` printed "Compiled with warnings" that I could not reproduce in two later builds (one of them forced). The 50 cap's error message is not checked in the wizard UI. Email rendering in real mail clients is still unchecked.

### M4 follow-up: the first real-send check against Resend (`fix:` commit)

With the domain `mail.brunchsters.com` verified in Resend (records added through Cloudflare's one-time authorization: two CNAMEs and a DKIM TXT on `mail`, plus a `_dmarc` TXT on the root), a local run (`INNGEST_DEV=1`, real key, Inngest dev server) was checked by hand:

- **Passed:** an invite email arrived in a real Gmail inbox (not spam) from `invites@mail.brunchsters.com`; SPF, DKIM and DMARC all report PASS in "Show original"; the invite and the confirmation email both rendered well on desktop and on an Android phone; the confirmation email reached the host and the invitee; Resend showed the sends as delivered and the Inngest dashboard showed the runs.
- **Found by replaying `invite/sent` after the brunch was confirmed:** Resend answered **409 `invalid_idempotent_request`** ("key used within 24 hours but the request body was modified"). Dedupe worked (no second email), but the body differed because confirming moves every live invite's expiry and the email prints that date, so the same key arrived with new text. Our adapter treated every unrecognized provider error as retryable, so the run retried with backoff and sat in "Running" before failing. The email had already been sent, so retrying could never help.
- **Fix:** `EmailError` gains `already_sent`; `ResendEmailService` maps `invalid_idempotent_request` to it (and keeps `concurrent_idempotent_requests`, a request still in flight, retryable); `sendInviteEmail` and `sendConfirmationEmail` turn it into a normal `skipped_duplicate` outcome so the run completes.
- **Tests:** 4 new unit tests (core 418, web 258): the adapter maps the 409 to `already_sent` and keeps the in-flight case retryable; both handlers return `skipped_duplicate`. **Proven to fail** by four mutations (the adapter ignoring the 409; the adapter also treating the in-flight case as sent; each handler dropping the mapping), each failing exactly its own test. **Verified live:** after the fix, replaying the same event through the Inngest dev server completed in about half a second with no new email and no step error (Resend still returns the 409; our code now treats it as done).
- **Also found:** running the e2e suite in dev mode while a normal `pnpm dev` and `inngest-cli dev` were up produced 3-5 unrelated failures in two runs (404 where 409 expected, a missing radio, timeouts), including with this fix stashed out, and went back to 75/75 when they were stopped. `docs/SETUP.md` previously said the suite was safe next to a running dev server; it now says to stop them first. The cause (a shared `.next` directory, CPU load from the queue's polling, or both) was not separated.
- **Still not exercised:** the "rejected recipient" path against real Resend (`validation_error`; every address we sent to was valid), Inngest Cloud mode, and sends to addresses at other providers (only Gmail was received).
