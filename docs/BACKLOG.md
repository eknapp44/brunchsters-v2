# Backlog: deferrals, follow-ups and open questions

Moved out of `PLANNING.md` §17 on 2026-10-24 (the text is unchanged; only its place and grouping are new), so that `PLANNING.md` stays the product and data-model reference and this file is the one place a deferral is written down.

**How to use it.**

- **One entry per deferral, here.** A spec's "What This Spec Does Not Cover" and an ADR's Consequences say what was left out and _why_, and link to the entry; they do not repeat its detail (the old rule of recording each deferral in three places drifted).
- **An entry names its origin** (the spec or ADR), what is deferred, and what would settle it. When it ships, mark it done in place and say where.
- **Old references still work:** "PLANNING §17 <name>" in earlier specs and ADRs means the entry of that name here.
- **New ideas** go under "Product candidates". The roadmap itself is the table in `PLANNING.md` §16 ("Roadmap after the core flow").

Candidates to weigh: a refresh on window focus, polling, or realtime (the notifications spec already plans a `RealtimeProvider`); the open questions are confusion (a ballot or roster changing under someone's hands, an option vanishing mid-vote), cost (queries and connections), and which screens earn it (votes, roster, invites, status). Needs `/spec-grill`; best with or just after the notifications spec. **Done in spec 0015 (M8):** the brunch page, the manage page and the dashboard refresh themselves when the person comes back to the tab (never within 15 seconds of the last refresh, while a request is on its way, over a ballot that has not finished saving, behind an open dialog, or just after a form was submitted), the bell's number is polled once a minute, and a polite live region announces vote-count changes someone else made (design-fidelity deferral 6 is closed; the person's own tap is silent). **Still open:** Realtime, so a page that stays in front of someone still changes only when they come back to it or act (see "Notifications deferrals"); the roster, the host's suggestion list and invites refresh on focus too but have no announcement; a person who is actively looking at a page while an outside vote lands a moment after their own tap has that one change absorbed by the own-tap rule (the page still shows it). (2) A **retry action** on a failure toast, if beta users ask (the copy promises nothing meanwhile). (3) An **offline queue or banner** (`network` is one line). (4) The host-facing "an email did not go out" signal stays with the notifications spec (**planned in spec 0015 M6**, invite emails only). (5) **Loading skeletons** (deferred 2026-10-25, after the M6 spike): a placeholder for the brunch page, the manage page and the dashboard while they are read. The spike (the attempt was not kept: a `Skeleton` primitive, page-shaped placeholders for the three pages, and journeys for the status guard, the placeholder and axe; it is quick to rebuild from this description) measured on a production build that (a) a `loading.tsx` turns a not-found page into a 200 for an outsider and a made-up id, and a `Suspense` boundary after the membership check avoids that, but (b) either way the page's controls hydrate later: the first checkbox was owned by React about 45 ms after `load` without a boundary and about 330 ms after with one, so a tap in that window is lost, and about ten journeys that click right after `load` failed consistently. Pages load in about 130 ms locally, so the placeholder buys little until real latency exists. **What would settle it:** measure the real time to first content on the deployed beta (the deployment spec); if it is long, decide how to avoid the hydration cost (a boundary only around the slow panels, with the controls outside it; streaming only on a client navigation; or a faster read) before bringing the branch back.

(1) **Rate limits** [wanted, before the beta]: nothing limits how many invitations a person can email (the app could be used to send spam), how often place search is called (it costs money through the Google Places key), or how often anything else is hit. **Done 2026-10-23: spec 0012 / ADR 0013** (Postgres counters behind a `RateLimiter`, caller-keyed, 429 with `Retry-After`, an inline line in the invite panel and place search). The wizard's _other_ invite failures (a 500, offline) are still ignored: see "Silent failures to surface". **When a spec adds the setting that lets attendees invite without the host's approval** (the column exists and defaults to "host approves"; nothing can change it yet), auto-approved suggestions spend the host's and the brunch's daily invite budgets, so one attendee could use a host's day up: decide a per-suggester budget in that spec (ADR 0013). Still open, for the deployment spec: **Strict-Transport-Security** and `upgrade-insecure-requests` (set with the real domain, never from localhost), confirming Vercel overwrites a client-supplied `x-forwarded-for`, and Dependabot (a repository setting; proposed in `docs/SETUP.md`, never written by the agent). (3) **Opening an invite link changes data on a GET** [owner: "odd for a GET to change data", and the auto-"yes" feels wrong]: today a signed-in person opening `/invite/<token>` is RSVP'd yes and redirected (spec 0004), and that page also adds them as an attendee. Direction: the page shows the preview with an explicit **Join** button (a POST), the brunch page then asks "You in?" with nothing chosen; the auto-"yes" goes away. Needs a journey change in the invitee journeys (A-series) and belongs with the feedback-surfaces spec, which touches the same controls. This supersedes design-fidelity deferral 4. (4) **Expired or invalid session mid-use** [owner: revisit]: what a person sees when their session ends while a page is open (a control's fetch gets a 401 and shows the generic error; a page load redirects to sign-in with a callback). The e2e server logs show `JWTSessionError` for the deliberately expired cookies; the real-user behavior has not been checked. Decide the wording and whether to send the person back where they were. **Partly done in spec 0014 (M5):** a tap refused as signed out sends the person to sign in with a callback to the same page (and the auth middleware's 401 is coded, so the client knows it). (5) **Account deletion** does not exist, so a soft-deleted user's row would still show in a roster (every read behaves the same way); decide with the Settings spec. (6) `callbackUrl` is now restricted to a path on this site (`safeCallbackPath`, unit-tested, journey P9). (7) A member opening the host-only manage page now gets a **403** (`forbidden()`, journey C3/H4), an outsider the same 404 as a made-up id.

## Product candidates

- **Product candidates raised after spec 0011 closed** (owner, 2026-10-22; none is specced or scheduled; each needs `/spec-grill`). (1) **Inviting people you know instead of typing emails.** The friends tables already exist (`Friendship`, `FriendGroup`, `FriendGroupMember`, with no UI, §8) and `BrunchAttendee` history already records who has brunched with whom. Recommended shape, in two phases: first a **"people you've brunched with" picker** in the invite panel (derived from past brunches, searchable by name, invites by user id so no email is shown; typing an email stays for people not on Brunchsters yet), with no request flow; then **explicit friends and groups** ("The Usual Crew") with the accept/decline states the schema already has. Searching all users is not allowed (it would let anyone enumerate accounts); the pool is people you share a brunch with, or accepted friends. Best after the notifications spec, so an invited existing user hears about it in the app. (2) **Pending suggestions inside the Locations and Times panels** on the manage page (a "Suggested" group under the approved options, each with Approve and Decline, beside Remove) instead of their own panel. Recommended, but **left out of the lifecycle spec on purpose (2026-10-23, owner)** to keep that spec to lifecycle: it needs its own spec, and it changes journeys that count list items and find "suggested by" (listed per milestone). Pending rows stay out of vote counts and out of the Confirm panel. (4) **Brunch wrap-up (end-of-life review)** (owner, 2026-10-23): once a brunch has happened, a short review of how it went (and what to do again), which would give the unused `completed` status a real meaning. Until then a confirmed brunch is only "Past" by derivation (`isPastBrunch`). Likely rides with the scheduler the notifications spec needs (reminders), which could also mark past brunches `completed` and add an "over" rule to `assertBrunchOpen` (spec 0013 leaves a past confirmed brunch accepting changes). Not specced or scheduled; needs `/spec-grill`. (3) **Separate closing times or separate confirmations for places and times.** Not recommended as separate deadlines (two clocks, more states, nobody has asked). A narrower idea worth watching: **staged confirmation** (lock the place early, keep voting on times); it fits the rule that times show in the place's timezone once the place is confirmed (§9.3), but it changes the status and lock rules and the confirmation emails, so it needs its own spec and real beta feedback first.

From spec 0015: confirm the 15-minute `run-scheduler` (completes past brunches, sends deadline reminders) and the daily `prune-notifications` are registered and firing in Inngest Cloud (the suite proves the function bodies by sending `scheduler/tick`, not the cron schedule). From spec 0012: confirm the daily `prune-rate-limits` cron function is registered and runs in Inngest Cloud (nothing fires its schedule in the test suite), that the host overwrites a client-supplied `x-forwarded-for` (Vercel's documentation says it does, to prevent spoofing; but with another proxy in front, such as Cloudflare, every visitor would arrive with the proxy's address and the invite-token address limit would lump people together, so the app's domain must be DNS-only or the real client address must come from a header the proxy sets and Vercel is told to trust), and that the CSP raises no console violation on any screen of the real deployment.

## Known bugs and gaps

- **Silent failures to surface** — **done in spec 0014 (2026-10-25) except the host-facing signal:** the creation wizard no longer ignores the invite request's response (the Invites panel says when a batch did not go out), the place search says when it could not answer, and every control words its failures from the code the route sent. **The host-facing signal is done in spec 0015 M6:** when an invite email fails for good (a refused address, or the provider failing until the queue gives up) the invite list says so beside Resend and the host gets an inbox row; a resend that goes clears both. **Still open:** the same signal for the other three emails (confirmed, called off, back on), which go to many people at once and would need a per-recipient record; and a host who is told only in the app (no email) if the queue itself is down, since nothing runs to write the row.
- ~~**Place search can show stale results.**~~ **Fixed in spec 0014 M5** (an abort per query and a guard on the pick; journey T8, proved to fail without the fix).
- **Brunch size cap** — nothing limits how many people a brunch can invite or accept (there is a minimum size, no maximum). Needs its own spec: does it count invited or "yes"? what does the host see at the limit? do suggestions respect it? Spec 0008 only bounds a single `sendInvites` request to 50 addresses (an input guard for email fan-out, not this cap).
- **Allow resubmitting a declined suggestion.** `BrunchInviteSuggestion` (spec 0004), `BrunchLocationSuggestion`, and `BrunchTimeSuggestion` (spec 0005) have no soft-delete — once a host declines one, that exact suggestion (same email / place / time) can never be resubmitted by anyone, for that brunch, ever. Raised during spec 0005's senior-architect review pass as a question, not a bug (it's spec 0004's existing, already-shipped behavior, consistently applied to spec 0005's new tables). User decided to fix all three rather than leave spec 0005 behaving differently from spec 0004. Scoped out of the spec 0005 branch because it touches already-shipped spec 0004 code and needs a real decision on resubmission mechanics (insert a fresh row reusing the old one's identity, or reset the existing row back to `pending`) — bigger than a pre-MR polish pass. Needs its own small spec; not yet started.

## Resolved (kept for the record)

- **E2E testing infrastructure (testcontainers + test-auth bypass + Playwright).** **Resolved — shipped as [ADR 0007](adrs/0007-e2e-testing-stack.md) / `specs/0006-e2e-testing-infra`; the proposal below changed in two ways: testcontainers is deferred (a dedicated e2e database on local Postgres / the CI service container instead) and there is no test-only `Credentials` provider (Playwright mints session cookies, so `auth.ts` is untouched).** Original proposal, after spec 0004: an ephemeral Postgres via `@testcontainers/postgresql` for integration tests (no dependency on a locally running Supabase instance), a test-only NextAuth `Credentials` provider gated behind an env flag (never reachable in production) so headless tests can log in as fixture users without real Google OAuth, and Playwright driving full multi-actor flows (invite → second account joins → RSVP → suggestion → approve) as automated regression coverage. Motivated by spec 0004's M5/M6 bugs (self-invite batch rejection, already-member collision) — both were only caught by manual two-account browser testing, never by unit/integration tests, because the bug required two different signed-in identities interacting with the same data. **Reinforced by spec 0005:** its voting/manage UI (M7/M8) had no browser or auth-bypass available at all, so verification fell back to hand-minting NextAuth session JWTs with `next-auth/jwt`'s `encode()` and driving the live dev server's HTTP surface directly — a real but one-off, non-reusable workaround that proved the server-rendered data and route handlers were correct without ever proving a checkbox click, a debounced search, or `router.refresh()` work in an actual browser. That gap (client-side interactivity, unverified) is recorded in `specs/0005-voting-and-confirmation/tasks.md`'s M7/M8 testing notes and its post-M8 review section. Candidate for CI (GitHub Actions runners have Docker by default, so both testcontainers and headless Playwright run there naturally). Author wants to push for including this before the initial release but is open to sequencing it after if it doesn't fit. Needs its own ADR (new libraries, new auth code path) and spec before implementation — not a milestone of any single feature spec.
- **Email addresses are compared case-sensitively across requests — RESOLVED by [spec 0007](../specs/0007-email-normalization/spec.md) / [ADR 0008](adrs/0008-normalize-email-addresses.md):** addresses are now stored and compared trimmed and lowercased, produced by `normalizeEmail` (the only constructor of the branded `Email` type) at the request schemas and at sign-in, existing rows were backfilled by a migration, and `CHECK` constraints make the database refuse anything else. Original finding, kept for the record — found by the e2e suite (spec 0006 M5): inviting `Case-X@Example.com` and later `case-x@example.com` creates **two** `BrunchInvite` rows — two links, two lines in the host's list — for one person. `sendInvites` de-duplicates case-insensitively only within a single batch and against the host's own address; the unique keys (`BrunchInvite[brunchId, invitedEmail]`, `BrunchInviteSuggestion[brunchId, suggestedEmail]`, `User.email`) are exact-string, and the known-user lookups (`user.findFirst({ where: { email } })` in `sendInvites`, `suggestInvitee`, `signInWithProvider`) are too, so a mixed-case invite can also miss an existing account. Needs a decision before a fix — normalize to lowercase at every write/lookup boundary vs. Postgres `citext` — plus a data migration for existing mixed-case rows, so it warrants a short ADR and its own small spec rather than a quick patch. Not yet scheduled.
