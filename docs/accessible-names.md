# Accessible names changed on purpose

The e2e journeys find controls by role and accessible name, so a rename is a contract change
(`apps/web/CLAUDE.md`, "Accessible names are a contract"). This file is the log: what each spec
renamed, so a journey that breaks on a name can be traced to the decision. Add to it when you rename
something; list the journeys you edited in the spec's `tasks.md`.

## Spec 0011, design fidelity

Dashboard (M2): the h1 `Dashboard` is now the greeting ("Morning, Evan"; "Hey, Evan" until the browser has filled the time in), so journeys wait on `expectDashboard` (`e2e/support/dashboard.ts`), never on one word of it; `No brunches yet.` is "The table's set. Now invite some people." (`EMPTY_DASHBOARD_HEADLINE`); rows and the next-up card word the status "Open for votes" / "In the works" (the brunch page badge keeps the lookup label); the next-up brunch is a card (`h2` = its title, a link "Open <title>"), not a row, and is not repeated in the list. Unchanged: `Plan a Brunch`, `Upcoming`, `Past`, the title link, `(Host)`, `N going`. Brunch page (M3): the RSVP buttons are `I'm in` / `Maybe` / `Can't` (in that order; the emoji are `aria-hidden`), the card heading is `You in?`, the ballots are `Where to?` and `When?` (the manage page keeps `Locations` and `Times`, so journeys use `ballot()` on the brunch page and `manageOptions()` on the manage page), the host's invite button is `Round up the crew`, and a confirmed brunch shows a `Brunch on.` heading and two `Locked in` chips. The status badge still reads exactly "Active", "Draft" or "Confirmed" once. "Who's coming" is plain grouped text (`role="group"`), not a list; a pending person's address appears in it and in the invite list, so a journey that means the invite list uses `inviteRow`. Creation wizard (M4): the main button of steps 1 to 3 is `Continue` (was `Next`; the page object's `next()` clicks it), the first step's progress name is `Title` (was `What`), each step has an `h2` heading (`Give it a name`, `Pick a spot`, `Pick a time`, `Round up the crew`) with an eyebrow "Step N of 4 · …", and `Cancel` is a link (top, left out on a phone, and in the first step's footer). `Plan a Brunch` is still the page `h1`. Front door and edges (M5): the landing page and the sign-in page share the h1 "Your friends are hungry. Probably." (journeys use `expectLandingPage` / `expectSignInPage` in `e2e/support/pages.ts`, which also look for something only that page has), the landing page's links are `Round up the crew`, `See how` and a small `Sign in`, the invite preview's h1 is the brunch title with "{host} wants you at brunch" above it (no status badge), an unusable invite says "That invite's gone cold.", every 404 says "This table's empty." and nothing more (it must never say "brunch", "private" or why), and the host's manage buttons are `Close voting` (was `Call it` until spec 0013, which renamed it so it is no longer a substring of `Call it off`) and `Lock it in`. After M7: a member who is not the host opening the manage page gets a **403** with the h1 "That one's the host's." (`HOST_ONLY` in `e2e/support/pages.ts`), while an outsider still gets the 404 text. Later milestones add their changes here.

## Spec 0013, brunch lifecycle

Manage page: an `End of the road` section with `Call it off` (dialog confirm; the safe button `Nope, keep it` has focus), `Bring it back`, and `Delete this brunch` / `Delete this draft` (dialog confirm `Delete it`, safe button `Keep it`); a called-off brunch's page has a `Called off.` banner and no RSVP, ballots or suggestion controls. `Hide from my dashboard` / `Unhide` on the brunch page, `Hide {title}` / `Unhide {title}` as an eye icon on dashboard rows, the next-up card and the Hidden list (the name is on the button and is its tooltip; the brunch page's header keeps the word), a `Hidden (n)` link and a `Show all` link for the Past cap. Close voting is `Close voting`, not `Call it`, so neither manage-page button name contains the other.

Later changes in the same spec: the manage page's close-voting button is **Close voting** (it was
**Call it** from spec 0011 until 0013, when it was renamed because it was a substring of **Call it
off**), and its nudge line says "close voting now if you're ready". The brunch page's Hide control is
in the header beside Manage brunch; on dashboard rows, the next-up card and the Hidden list it is an
eye icon whose `aria-label` and tooltip are `Hide <title>` / `Unhide <title>`.

## Spec 0014, feedback surfaces

No button, link, label or heading is renamed. What changes is the error and result text, and the role it sits in (a failure that was a `role="alert"` line under a control becomes a toast in one polite `status` region, or stays an inline `alert` where the person must fix or wait it out).

- **M2, RSVP:** the "Failed to update RSVP" `alert` under the buttons is gone; a failure toasts "Something went sideways on our end." (or the line for the code the route sent, for example "This one's been called off, so it can't change."), and a success toasts "You're in. See you there." / "Maybe it is. You can change it any time." / "Got it, you can't make it." New: the toast region (`role="status"`, `aria-live="polite"`, always present, empty until a toast) and a **Dismiss** button on each toast. The RSVP buttons (**I'm in**, **Maybe**, **Can't**) keep their names; while a save is out they are `aria-disabled` instead of `disabled`, so keyboard focus stays on the button that was pressed. Journey edited: P6 in `brunch-page.spec.ts`; new: T1 and T2 in `feedback.spec.ts` (words in `e2e/support/toasts.ts`).
- **M3, ballots, invites and voting controls:** no name changes; the error text and its place change. **Ballots:** the inline `alert` beside a ballot that said "Failed to save your vote" is worded from the code the route sent ("Voting's closed on this one." for a real refusal, "That one just came off the table. Have a look at what is left." when an option was removed under the voter, "Something went sideways on our end." for a 500, "Looks like you're offline." offline) and stays inline; after a failure that means the page is out of date (option removed, voting closed, called off) the page is asked again. **Invites:** a failed send is an inline `alert` under the field (the typed address stays); a failed resend or revoke is a toast; a resend that goes out toasts "Sent again."; **Copy link** toasts "Link copied." (the button still reads **Copied!** for a moment) or, when the browser refuses the clipboard, "That didn't copy. Your browser wouldn't let it." (it used to fail without a word). Round up the crew, Resend and Revoke are `aria-disabled` instead of `disabled` while a request is out. A refused resend or send (429) is still the row's or the panel's own inline wait, never also a toast. **Voting controls:** "Failed to update the voting deadline" is an inline `alert` in voice beside the field; a saved deadline toasts "Deadline saved." ("Deadline cleared. Voting stays open." when emptied); "Failed to close voting" is a toast. **Save deadline** and **Close voting** are `aria-disabled` while a request is out. Journeys edited: F1 (`failure-paths`), R3 and R4 (`redux-ui-state`), L4 (`rate-limits`: the 429 body is coded), H2 (`closing-voting`) and H8 (`manage-options`: they asserted a route's raw error body, now its code); new: T3, T7, T10, T11 in `feedback-controls.spec.ts`.
- **M4, the remaining controls:** no button, link, label or heading is renamed; the error text and its place change, and the generic "Failed to …" strings are gone from every control. **Inline (a field or a choice the person made, or a dialog):** a failed add of a place or time (the manage page), a suggestion of a place, time or person, locking it in, and a failed call-off or delete (inside its dialog, where it is seen) are an `alert` in voice beside the control (the typed value stays); a refusal that means the brunch moved on (already locked, an option removed, called off) also asks the page again. **Toast (one tap, nothing to fix):** removing a place or time, Approve and Decline on a suggestion (invite, place or time), **Bring it back**, and **Hide** / **Unhide**. A hide from the brunch page says it once ("Off your dashboard. Nobody else sees a change." / "Back on your dashboard."); on a row the row moving is the sign. Real refusals now read as their own lines: the last option is "That's the last one on the table, so it has to stay.", a repeat suggestion is "That one's already on the list.", locking an already-locked brunch is "This one's already locked in.". Pending buttons (**Remove**, **Approve**, **Decline**, **Lock it in**, **Add Time**, **Suggest**, **Bring it back**, **Hide**) are `aria-disabled` instead of `disabled`. The signed-out 401 from the middleware is coded too. Journeys edited: F3 (`failure-paths`: the last-option refusal is a toast), H5-style confirm and H8 (`manage-options`), the repeat-suggestion case in `same-person`, and the API-authorization journey (every refusal carries its code: signed_out, forbidden, not_found, and an outsider's body equals a made-up id's); new: T12, T13, T14, T15 in `feedback-controls.spec.ts`.
- **M5, the wizard, the place search and a session that ends:** no button, link, label or heading is renamed. **Wizard:** a failed create is still the red line under the step, but worded from the code the route sent ("Something went sideways on our end." for a 500, "Looks like you're offline." offline, "That didn't look right. Check it and try again." for a refused form) instead of whatever text the route had; the validation messages the route used to pass through are gone (the wizard checks its own fields). **Invites that did not go out:** after a brunch is created with an invite batch that failed (not a refusal for the day's budget, which the page already shows as a wait), the Invites panel carries a `status` line above the field: "Your brunch is up, but the invites didn't go out. Add the addresses again below." It stays until an invite is sent (or the page is reloaded: the store is per mount). **Place search:** a search that could not be answered shows an `alert` beside the input ("Our end hiccuped. Give it a minute, then try again." or "Looks like you're offline."), where it used to show nothing; it goes with the next answer. **A session that ends mid-use:** a tap that is refused as signed out sends the person to `/sign-in?callbackUrl=<this page>`. Journeys edited: F2 (`failure-paths`: the create failure is worded from the code); new: T4, T6, T8 in `feedback-controls.spec.ts`.

## Spec 0015, notifications

Nothing existing is renamed; these are new. The names to know before touching the screens:

- **M4, the bell and the inbox:** the top bar gains a link named **`Notifications`**, or **`Notifications, N unread`** (`Notifications, more than 99 unread` past 99); the visible number is `aria-hidden` because the name already says it. It sits in the `Account` navigation, before the person's initials, and carries `aria-current="page"` on `/notifications`. Because its name starts with "Notifications", a journey that looks for a link by a bare "Notifications" substring finds it on every signed-in page; use `bell()` (`e2e/support/inbox.ts`). The page `/notifications` has the h1 **`Notifications`**, a **`Mark all read`** button (disabled when nothing is unread, `aria-disabled` while the request is out), one link per row whose name is the row's words (an unread row's name starts with "Unread."), and **`Show older`** when there is more. The empty inbox says **`Nothing yet.`** with the link **`Plan a Brunch`** (the same name as the dashboard's, on a different page).

- **M6, the failed invite:** new, nothing renamed. A row on the host's invite list whose email did not go out gains a line **`That email didn't go through. Try Resend, or copy the link and send it yourself.`** (an `InlineAlert`, no live region: it is there when the page loads). The inbox row reads **`Your invite to {address} didn't go through`**. Journeys find the row by the address (`inviteRow`), so the line does not change any existing name.
- **M5, settings and mute:** new, nothing renamed. The inbox gains a link **`Notification settings`** (beside "Mark all read"), which opens `/settings/notifications`: the h1 **`Notification settings`**, a link **`Back to notifications`**, three h2s (**`Your brunches`**, **`Reminders`**, **`When you host`**) and one `switch` per choice named **`{line}, in the app`** or **`{line}, by email`** (for example `A brunch is on, by email`; the visible caption is only "In the app" or "By email", and the name contains it). A switch is `aria-disabled` while it saves, never `disabled`, so the keyboard keeps its place. The brunch page gains a section with the id `notifications` (the target of the "Mute this brunch" link in the emails): a `group` named **`Notifications for this brunch`** with three radios whose names start **`All`**, **`Just big stuff`** and **`Muted`** (each has a hint line, which is part of its name, so a journey uses `/^Muted/`). The host also reads one line saying a failed invite always gets through.
